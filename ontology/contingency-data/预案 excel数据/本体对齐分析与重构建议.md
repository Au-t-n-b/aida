# 预案 Excel 数据 ↔ `预案schema` 本体 — 对齐分析与是否重构建议

> 目的：把 `预案 excel数据/`（22 张 §3.3.2 输出表）作为 `预案schema/`（object-types.json + link-types.json + datasource-bindings.yaml）的**数据来源**，分析两者差别，并判断**是否需要根据数据重新构建本体**。

---

## 一、结论（TL;DR）

**不需要推倒重建，但需要一次"扩展 + 绑定"改造。**

- 本体的**决策/评估骨架**（ContingencyPlan→UseCase→DecisionPoint→Evidence/Assessment→Gap/Task/Risk/Assumption + RemediationTask「modifies」资产 + ConfigurationFile）设计自洽、与 `04`§19 决策引擎一致 —— **保留，不动**。
- 本体的**资产/配置层**（设备/部件/软件/组网/机房/服务/维保/SLA/验收/集成/责任矩阵等）只是"够决策评估引用"的薄模型，**不是 18 输出表的忠实数据模型** —— 需要补对象、补属性、改类型、改结构。
- `datasource-bindings.yaml` 当前 **全部 `sources: []`、`reader: metadata_only`**，即**一条数据源都没绑**。要让 Excel 进本体，这一步是**硬性前置**。

> 一句话：**本体当前是「可交付性决策模型」，不是「预案输出表存储模型」。** 把 Excel 当数据源，需要把资产层从"决策附属薄模型"扩展成"输出表忠实模型"，并补齐绑定。

---

## 二、两者定位差异（根因）

| 维度 | `预案 excel数据`（我构造的 22 表） | `预案schema` 本体 |
|---|---|---|
| 设计目的 | §3.3.2 **交付预案输出表**（人/货/站全量配置） | **方案可交付性评估**决策模型（localGeneration.useCase=方案可交付性评估） |
| 形态 | **扁平、反范式**、单预案快照、带预案版本号 | **图模型**：对象 + 外键链接；资产**无 planId**、可复用 |
| 资产与预案关系 | 表本身即"本预案的产出" | 资产**plan-independent**，仅经 `RemediationTask.modifies*` 间接关联（object-types 注释原文：「Reusable infrastructure assets are linked separately and do not carry planId」） |
| 风险/假设 | 独立两张表（预案上下文） | `RiskItem/AssumptionItem` 是**评估产物**，`assessmentId` 为 **required**（必须挂在某次评估下） |
| 主键/系统列 | 多数表无 id/name/status | 每个对象**强制** `{主键, titleProperty, status}`（required） |

## 四、四类差异明细

### 差异① 缺对象类型（4 个，必须新增）
| 输出表 | 建议新对象 | 关键属性 |
|---|---|---|
| 集群设备清单表 | `ClusterDeviceInventory` | clusterId/类型/超节点ID/存储集群ID/zone/ccae/dme/设备类型/厂家/型号/用途/命名起止/数量 |
| 测试用例表 | `TestCase` | l1/l2/l3 分类/用例编号/名称/目的/组网/预置条件/步骤 |
| 合同信息 | `ContractInfo`(+`ContractBoqItem`) | 合同ID/名称/金额/签署日期/签约方 + BOQ 行 |
| 项目基础信息 | `ProjectBasicInfo` 或扩 `ContingencyPlan` | 项目ID/项目编码/Proposal号/机会点编码/PD/TD/PCM/地点/待交付合同 |
| 预案版本历史 | `PlanVersionLog`（子表） | 版本号/创建人/创建时间/修改人/修改时间/本次描述/累计记录/摘要 |

### 差异② 缺属性（在已有对象上补，约 20 项）
- `EquipmentConfig`：+`vendor`(厂家) +`productCode`(产品编码) +`dataSource`(来源)
- `ComponentConfig`：+`dataSource`
- `SoftwareConfig`：+`remark`
- `NetworkConfig`：+`deviceRole`(设备角色) +`serverRole`(网管角色) +`dataSource` +`remark` +`isSelected`(共平面勾选)
- `ServiceConfig`：+`hierarchyLevel`(层级) +`serviceContentName` +`dataSource`
- `SlaRequirement`：+`hardwareSupport`(硬件支持)
- `ResponsibilityMatrixItem`：+`techStack`(技术栈)
- `AcceptanceStrategy`：+`paymentMilestone`(回款里程碑)
- `RiskItem`：+`riskPoint/impact/riskType/source/identifiedAt/closedAt/state`
- `AssumptionItem`：+`source/closeStatus`

### 差异③ 类型 / 结构不匹配（需改 dataType 或重塑数据）
- `EquipmentConfig.unitSpace/totalSpace/unitPower/totalPower` = `number`，数据是「42 U」「54 kW」→ 改 `string`，或拆「数值+单位」两列。
- `MachineRoomConfig.power` = `number`（同上）。
- **机房机柜信息表**：我表是 PoD 行 × 机柜组列；对象是单机柜行 → 二选一：把数据 unpivot 成单机柜行，或把对象改成 PoD 中心。
- **ServiceConfig 合并**：13+14 两张 Excel 喂同一对象但字段互斥 → 用 `serviceKind` 判别 + 双文件绑定，**或**拆成 `ServiceDeliveryConfig` + `ServiceContentItem` 两对象（推荐拆）。
- **NetworkConfig 合并**：07+08+09 三张 Excel → 一对象，靠 `networkType` 判别 → 同理，建议拆 `NetworkPlane`/`CommonPlaneType`/`MgmtServer` 或保留单对象 + 判别列。

### 差异④ 体系性缺口（跨所有表）
1. **主键/系统列缺失**：22 张 Excel 多数无 `id / name / status / updatedAt`，而每个对象 required 这些 → ETL 必须**合成主键**（如 equipmentId=产品编码+版本）、title、`status=ACTIVE`。
2. **资产无 planId 的复用模型 vs 单预案快照**：本体资产可复用、不带 planId；我的 Excel 是"本预案产出、带版本号"。**这是是否"扩展 vs 局部重构"的分水岭**（见第六节决策点）。
3. **风险/假设语义错配**：本体里它们是 `assessmentId` required 的评估产物；预案侧是独立两表（`04`§18 归项目管理）→ 不应硬塞进 `RiskItem/AssumptionItem`，或放宽 required。
4. **datasource-bindings.yaml 全空**：需逐对象写 `reader: excel`、`sources: [文件名]`、列名→apiName 映射。

## 五、是否"重新构建本体"？—— 判断

| 选项 | 适用前提 | 工作量 | 结论 |
|---|---|---|---|
| **A. 推倒重建** | 本体方向错了 | 大 | ❌ 不必。决策/评估/任务/链接骨架是对的、且是另一层关切 |
| **B. 扩展 + 绑定**（推荐） | 骨架保留，资产层补齐 + 补绑定 | 中 | ✅ 推荐。+4~6 对象、+~20 属性、改 6 处类型/结构、填 bindings |
| C. 只做 ETL 适配（不改本体） | 接受信息丢失 | 小 | ⚠ 仅当只为"灌点数据演示"；会丢 来源/版本/合同/测试用例/集群 等大量字段 |

**推荐 B**，理由：18 输出表是业务事实、相对稳定；本体资产层是为决策"够用"而裁剪的，本就预期会随真实数据补全（这正是"根据数据完善本体"的常规演进，与记忆中 value-types/function-registry 等增量一致）。

## 六、关键决策点（需你拍板，影响改造形态）

1. **预案归属模型**：资产是否带 `planId`/`planVersion`？
   - A 选项：给资产加 `planId`（Excel 即单预案 SSOT，简单直接，但偏离"可复用资产"原设计）。
   - B 选项：保留无 planId，新增 `Plan_Includes_*` 链接层，由 ETL 生成"预案↔资产"成员关系（更 Palantir、更复杂）。
   - 倾向：**先 A-lite**（资产加可空 `planId`），快速打通；后续要复用再演进到 B。
2. **合并对象拆不拆**：ServiceConfig / NetworkConfig 维持"单对象+判别列"还是拆多对象？倾向**拆**（更贴近 18 表、绑定更直观）。
3. **机房表形状**：unpivot 成单机柜行，还是新建 PoD 中心对象？倾向**新建 `PodCabinetLayout`**（保留 PoD×机柜列的业务直觉）。
4. **风险/假设**：放宽 `assessmentId` required 以承载预案侧两表，还是保持评估产物语义、预案侧风险另走项目管理？倾向**保持语义**，预案侧风险不入本体（与 `04`§18 一致）。

## 十一、合一收敛 · 第一步（已实施）

> 结论：Palantir 终态是「一个 Ontology」，但现在**先分开、分步收敛**（预案未稳定 + 概念重叠未去重，裸合并更糟）。本步只做**零运行风险**的两件事。

**1) 把预案 schema 从 gitignored `bak/` 提升到受跟踪目录（仍是独立 ontology）**
- `backend/bak/预案schema/` → **`backend/schema-contingency/`**（6 文件：object/link/action/datasource-bindings/value/interface-types）。
- 改 3 处路径默认值：`backend_app.py`(DELIVERY_CONTINGENCY_SCHEMA_DIR)、`datasource_bindings.py`(_contingency_bindings_path)、`tests/test_schema_driven_backend.py:1032`；并更新 `bak/` 两个生成脚本的 SCHEMA 路径，便于后续刷新。
- 计划运行**完全不受影响**：default 仍只读 `backend/schema/*.json`；区分方式不变（ontology id + 目录，`ONTOLOGY_SCHEMA_DIRS` 显式注册，无 glob 自动发现）。

**2) 收敛共享语义层（接口词表对齐）**
- `backend/schema-contingency/interface-types.json` 改为 **`ProjectScoped` + `SourceTraceable`（与计划本体运行时定义逐字节一致）+ `PlanScoped`（预案侧作用域接口，与 ProjectScoped 同模式）**。
