# 预案本体数据方案

> 方案分析：预案相关本体的结构化数据集如何开发、存储与摄取进 Dolt。
> 结论先行：**不要做「多版本 CSV」**。Dolt 本身就是 git-for-data，让它当版本层，CSV/JSON 降级为编辑与交换格式；层级数据改 JSON，扁平数据每个 ObjectType 一张表；「模板」与「运行记录」拆开。

## Summary

- 你描述的「多版本 CSV → 自动摄取 Dolt」会形成**两套版本系统**（文件名版本 + Dolt commit 版本），二者必然漂移——现有 `dolt_mirror.validate_main_mirror` 的 `missing/extra/mismatched` 检测就是漂移存在的证据。
- 仓库已经实现了大半个 Palantir Foundry facade（Dataset 事务、分支沙盘、schema 驱动建表、镜像 + 漂移校验）。预案要做的不是另起炉灶，而是**把真实数据接上这套既有机制**。
- 推荐**单一事实源 + 声明式摄取 + 三层分工**：git 编辑层（模板）→ Dolt main 服务/版本层 → Dolt 分支推演层（运行态）。
- 预案是「策展型模板数据」（决策树、触发条件、阈值），不是高吞吐事实表，所以 **CSV 改为 JSON/YAML 表达层级**，扁平明细沿用「每个 ObjectType 一张 CSV」。
- 关键补强：Foundry 式的 **writeback 分离**——「预案模板/参考数据」与「运行时决策记录」必须是不同 ObjectType + 不同 dataset，生命周期不同。

## 现状（已具备的能力）

| 层 | 现有实现 | Foundry 对应 |
|---|---|---|
| 数据源声明 | `backend/schema/datasource-bindings.yaml`（ObjectType→reader→CSV/JSON） | Ontology datasource mapping |
| Schema 驱动 | `backend/schema/object-types.json` 驱动建表 | Ontology Object Types |
| 数据集事务 | `backend/dataset_service.py`（`APPEND/UPDATE/SNAPSHOT` + upload + commit） | Datasets + Transactions |
| 多版本/沙盘 | `backend/scenario_lifecycle_manager.py`（分支级 engine、publish/discard） | Dataset branches + Scenarios |
| 镜像 + 漂移检测 | `backend/dolt_mirror.py`（`sync_main_mirror` / `validate_main_mirror`） | Ontology sync + lineage |

预案本体（`delivery-contingency-plan`：`ContingencyPlan` / `DecisionPoint` 等）目前是 **metadata-only、无 backing data**，位于 `backend/bak/预案schema/`（gitignored），用于 DRB 决策评审，尚未进 bindings、也未进 Dolt。

## 核心判断：为什么不要「多版本 CSV」

- **Dolt 就是 git-for-data**，其 commit graph 即「多版本」，分支即 what-if。在它之上再叠 `plan_v1.csv / plan_v2.csv` 等于重复造版本层。
- Foundry **从不用文件名表达版本**：版本 = transaction/commit，分支 = branch。仓库已体现这点（`TRANSACTION_TYPES = {APPEND, UPDATE, SNAPSHOT}` + Dolt 分支沙盘）。
- 两套真相并存的代价已经显现：`validate_main_mirror` 的漂移检测，本质是「CSV 真相」与「Dolt 真相」打架时的补丁。
- **决策：选唯一事实源（SoT），CSV/JSON 只当编辑与交换格式。**

## Palantir 借鉴 vs 不必照搬

值得借鉴（多数已有，差一点）：
- ✅ Dataset = 带事务的版本化表，不是文件堆 —— 已有。
- ✅ Schema 声明一次，摄取向 schema 看齐 —— 已有（`object-types.json`）。
- ✅ 显式 PK + 属性映射 —— 已有；**Link Types（Plan→DecisionPoint→Option）需补**。
- ✅ 分支做 what-if、主干做发布 —— 已有。
- ⚠️ **写回分离（writeback）**：Foundry 把「管线产出数据」与「Action 编辑数据」分成两个 dataset 再叠加；预案的「模板」与「运行记录」必须照此拆开 —— **目前缺**。

不必照搬：
- ❌ Spark/Parquet 全套管线 —— 对策展型小数据是杀鸡用牛刀；Dolt 的分支能力反而更契合 what-if。
- ❌ Foundry Build 编排 —— 一个幂等 SNAPSHOT 脚本足矣。

## 推荐方案：三层分工

```
① 编辑层（git）            ② 服务/版本层（Dolt main）        ③ 推演层（Dolt 分支）
结构化模板文件        ──→   幂等 SNAPSHOT 摄取          ──→    预案触发/决策记录/场景改动
PR review = 治理           Dolt commit = 多版本历史            publish / discard
版本 = git commit          可 diff / 可回滚                    运行态绝不回写 CSV
```

选「git 编辑 + Dolt 服务」而非纯 Dolt-as-SoT 的理由：数据集与本体**同一团队**开发、预案是**策展型模板**。对这种靠评审把关的数据，**git PR 是最便宜的治理手段**；Dolt 提供服务态可查询 + 分支推演。两者各司其职，不抢 SoT。

### 数据形态建议（"csv 可改"的落点）

| 数据特征 | 存储格式 | 理由 |
|---|---|---|
| 层级决策逻辑（Plan→DecisionPoint→Option 树、条件表达式） | **JSON/YAML**，每个预案一个文件 | CSV 表达不了嵌套；JSON 在 git 里 diff 友好；已有 `json_sections` reader 先例 |
| 扁平明细（阈值表、风险-预案映射、SLA 参数） | **每个 ObjectType 一张 CSV**（沿用 `csv_table`） | 直接映射 Dolt 表 + PK + 外键，最省事 |

注意：是「**每个对象类型一张表**」（规范化、带 PK/FK），**不是**「同一份数据的多个版本文件」。

## Key Changes（落地步骤，全部复用现有模块）

1. **纳入 schema**：在 `backend/schema/object-types.json` 增加 `ContingencyPlanTemplate / DecisionPoint / DecisionOption`，声明 `primaryKeyPropertyApiNames` 与属性。
2. **加绑定**：在 `backend/schema/datasource-bindings.yaml` 增绑定——层级部分用新 `json_tree` reader（仿 `json_sections`），扁平部分用 `csv_table`；`writable` / `derived` 按「模板=只读、运行记录=可写」区分。绑定后会**自动**流经 `dolt_mirror.sync` / `validate` 与 dataset transaction 链路。
3. **补 Link Types**：定义 Plan→DecisionPoint→Option 链接——这是预案作为「决策树」可被本体查询/推理的关键（Foundry 的核心价值在 Link）。
4. **模板 / 运行记录分离**：
   - `ContingencyPlanTemplate`（git 编辑、`SNAPSHOT` 入 main、只读）
   - `ContingencyPlanExecution` / `DecisionRecord`（运行时经 Action/transaction 写 Dolt 分支、可写）
5. **what-if 走分支**：预案推演（「若触发预案 X 会怎样」）直接用 `scenario_lifecycle_manager.create_scenario` → 改动 → `publish/discard`，运行态零回写 CSV。
6. **单一摄取路径**：模板更新只走 `dataset_service` 的 `SNAPSHOT` transaction（或 `dolt_mirror.sync_main_mirror`），**不另写预案专用 importer**，避免再造一条会漂移的真相。

## Test Plan（验证）

- **摄取幂等**：同一份模板文件连续 SNAPSHOT 两次，Dolt 表行数与内容不变，`validate_main_mirror` 返回 `ok`（无漂移）。
- **层级完整性**：`json_tree` reader 解析后，Plan→DecisionPoint→Option 的 Link 在本体侧可遍历，孤儿 DecisionPoint/Option 被校验拒绝。
- **模板只读**：对 `ContingencyPlanTemplate` 发起 writable transaction 被拒；运行记录 ObjectType 可写。
- **分支推演隔离**：在场景分支改预案不影响 main；`publish` 后 main 可见、`discard` 后分支物理删除（沿用现有沙盘单测断言）。
- **漂移可检测**：人为令 git 模板与 Dolt main 不一致，`validate_main_mirror` 报 `drift` 并给出 `missing/extra/mismatched` 样本。
- 验证命令：`python -m unittest discover backend/tests`。

## Assumptions / 待确认的关键岔路

整个推荐建立在「预案模板由团队在**设计期**维护、靠 PR 评审」这一假设上，它决定 SoT 选择：

- **设计期维护、PR 评审** → 采用本方案「git 编辑 + Dolt 服务」。
- **若需业务人员/Agent 在运行期直接编辑、或大量按场景改写** → 翻转为 **Dolt-as-SoT**：用 Action/transaction 直接写 Dolt，CSV/git 仅作导出备份；`dataset_service` 已支持此路径。

其他假设：
- 预案数据规模属「策展型小数据」，无需 Spark/Parquet。
- 层级逻辑用 JSON/YAML，扁平明细用规范化 CSV（每 ObjectType 一表），均以 git commit 而非文件名表达版本。
- 运行态决策记录与模板分属不同 ObjectType / dataset，生命周期独立。

## 一句话总结

不缺机制（Dataset/分支/镜像都有），缺的是「别再用文件名做版本」——让 Dolt 当多版本层，CSV 降级为交换格式，层级数据改 JSON，并把「模板」与「运行记录」拆开。
